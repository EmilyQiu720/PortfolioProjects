# Payment Fraud SQL Intelligence Platform

## Goal

Build a production-style PostgreSQL analytics system for payment fraud monitoring, merchant risk scoring, customer behavior analysis, chargeback investigation, and SQL governance.

## Business Problem

Payment platforms need to approve legitimate payments quickly while detecting high-risk behavior before losses become chargebacks. This project models a realistic payment domain and implements SQL assets for:

- Fraud velocity detection across cards, accounts, devices, and merchants
- Merchant risk monitoring and chargeback rate analysis
- Customer behavior analytics with cohort-style activity metrics
- Operations dashboards for review queues and alert triage
- Data quality checks, audit logging, role-based access, and PII-safe views
- Performance tuning with index design and query rewrites

## Why This Project Is Portfolio-Grade

This is not a simple SQL query collection. It demonstrates the way a senior analytics engineer or data engineer would structure a database-backed risk platform:

- Normalized OLTP-style source model with strict foreign keys
- Business constraints for transaction amounts, statuses, and risk scores
- Index strategy for fraud lookups, time-window scans, and dashboard filters
- Analytical views and materialized views for reusable business metrics
- Audit triggers for sensitive table changes
- Role-based access and masked PII views
- Data quality tests for duplicate, orphaned, invalid, and inconsistent records
- Transaction integrity tests for review and chargeback workflows
- Performance notes with slow-query and optimized-query examples

## Data Model

The schema models payment risk across the following entities:

- `customers`: account holders with KYC status and risk tier
- `accounts`: customer-owned wallets or payment accounts
- `merchants`: businesses receiving payments
- `payment_methods`: cards, bank accounts, wallets, and tokens
- `device_fingerprints`: device and network signals used in fraud detection
- `transactions`: payment attempts and final settlement status
- `transaction_events`: event stream for authorization, capture, refund, and failure lifecycle
- `risk_rules`: configurable fraud rules with severity and thresholds
- `fraud_alerts`: alerts generated by SQL risk logic or manual analysts
- `manual_reviews`: human-in-the-loop review decisions
- `chargebacks`: disputes, reason codes, losses, and win/loss outcomes
- `audit_log`: immutable audit trail for sensitive changes

## SQL Engineering Highlights

### Fraud Detection

The fraud queries include:

- Card velocity: many transactions on the same payment method in a short window
- Device fan-out: one device used by multiple customers
- Merchant burst detection: sudden spikes in transaction volume
- High-risk transaction scoring: combined risk score using amount, country mismatch, chargeback history, and rule severity
- Review queue prioritization: alerts ranked by severity, amount, and age

### Analytics

The analytics layer includes:

- Merchant chargeback rate
- Merchant approval rate
- Gross payment volume by month
- Average order value
- Customer activation and repeat behavior
- Payment method risk distribution
- Manual review aging and analyst throughput

### Governance

The project includes:

- PII-safe analyst views
- Role examples for analyst, investigator, and admin access
- Audit triggers for transactions, manual reviews, and chargebacks
- Data quality tests that return failing rows
- Transaction tests for high-risk operational workflows

## How To Run

This project targets PostgreSQL 15+.

Start a local database:

```powershell
docker compose up -d
```

Run all SQL files in order:

```powershell
python scripts/run_sql_project.py --execute
```

Run static project validation only:

```powershell
python scripts/run_sql_project.py --check-only
```

The script prints the SQL execution order and can execute the project when `psql` is available on the machine.
